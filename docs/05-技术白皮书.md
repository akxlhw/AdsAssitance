# 技术白皮书

> **CoupangAds — AI 电商内容生成系统**
> 
> 面向技术决策者与架构师的技术原理说明

---

## 1. 技术愿景

构建一套**简单可依赖、模型无关、模板驱动、容错优先**的 AI 内容生产基础设施，让跨境卖家以最低的技术成本获得本土级的内容质量。

---

## 2. 核心技术选型

### 2.1 大语言模型（文本生成）

| 模型 | 提供商 | 适用场景 | 优势 |
|------|--------|---------|------|
| Gemini 2.5 Flash | Google | 商品画像、文案生成 | 多模态强、韩文理解好、速度快 |
| Doubao-seed-2-0-lite | 字节跳动 | 商品画像、文案生成 | 国内访问快、成本低 |

**选型逻辑**：
- 文本生成是系统的灵魂，决定内容的转化基础
- 采用双模型冗余架构，主备自动切换
- 不绑定单一模型，未来可无缝接入 Claude、Qwen、GPT-4o 等

### 2.2 多模态图像模型（图片生成）

| 模型 | 提供商 | 适用场景 | 优势 |
|------|--------|---------|------|
| Gemini 2.5 Flash Image | Google | 详情页图片生成 | 文字渲染准确率高、产品还原度好 |
| Doubao-seedream-5-0 | 字节跳动 | 详情页图片生成 | 速度快、国内稳定 |

**选型逻辑**：
- 电商图片的核心指标是**产品还原度**与**文字渲染准确率**
- 优先选择支持参考图输入的模型，确保产品外观一致性
- 2:3 竖屏比例的稳定输出是关键验收标准

### 2.3 图像处理引擎

- **Pillow**：图像加载、格式转换、RGB 转换、缩放
- **pillow-heif**：HEIC/HEIF 格式支持（iPhone 默认格式）

**处理流程**：
```
原始图片 → 格式识别 → HEIC 解码 → RGB 转换 → 长边缩放到 1536px → 传入模型
```

### 2.4 文档解析引擎

基于标准库实现，零外部依赖：
- `zipfile`：解压 DOCX 文件
- `xml.etree.ElementTree`：解析 Word XML 提取纯文本

**优势**：无需安装 `python-docx` 等第三方库，降低依赖复杂度。

## 3. 系统架构原理

### 3.1 分层架构

系统采用四层架构：

| 层级 | 职责 | 核心特点 |
|------|------|---------|
| 表现层 | CLI 入口 | 三个独立入口，功能对等 |
| 编排层 | 任务编排与状态管理 | 文件系统状态推断，零数据库 |
| 业务逻辑层 | 内容生成逻辑 | 纯函数设计，无副作用 |
| 适配层 | 模型 API 封装 | 统一接口，模型无关 |

### 3.2 对话模式 vs 独立请求模式

**文本链路**采用**对话模式**（同一个会话上下文）：
- 优势：上下文连贯，下游步骤可引用上游内容
- 优势：减少 token 消耗（无需重复发送完整产品上下文）
- 适用：商品画像 → 标题 → 关键词 → 卖点 → INS 文案

**图片生成**采用**独立请求模式**（每次全新请求）：
- 优势：每张图片请求携带完整显式上下文和参考图
- 优势：单张失败不影响其他图片
- 适用：18 张详情页图片的批量生成

### 3.3 状态持久化机制

系统采用**文件系统作为唯一状态存储**：

```
状态(State) = f(输出目录文件列表, CLI 参数)
```

**状态推断规则**：
- 输出文件存在 + 非强制覆盖 + 上游未变更 → COMPLETED（跳过）
- 输出文件不存在 → PENDING（执行生成）
- 强制覆盖模式 → FORCED_REGEN（重新生成）
- 上游文件更新于当前文件 → STALE（重新生成）

**优势**：
- 无需数据库，降低部署复杂度
- 天然支持「查看输出」和「手动删除重跑」
- 断点续跑逻辑通过文件存在性即可实现

## 4. 核心算法原理

### 4.1 智能参考图筛选

**问题**：从 N 张实拍图中选出 3 张最适合 AI 生图参考的图像。

**方案**：
1. 将全部实拍图重新发送给多模态模型
2. 请求模型基于「产品主体清晰度、色彩还原度、细节展示完整性」三个维度评估
3. 模型返回排序后的文件名列表
4. 系统取前 3 张作为参考图

**过滤规则**：
- 自动排除文件名含 `generated`、`screen` 等疑似 AI 生成图
- 确保选出的图片均为主产品实拍图

### 4.2 卖点结构化解析

**问题**：模型返回的卖点文案为自由格式 Markdown，需要解析为 B1-B9 结构化数据。

**方案（多层容错）**：
1. 优先匹配 `**B1**` 或 `## B1` 等 Markdown 标题标记
2. 次优先匹配 `B1.`、`B1、`等编号格式
3. 兜底策略：按行号分段，假设 B1-B9 均匀分布

**输出**：JSON 格式的 B1-B9 结构化数据，供下游图片提示词组装直接使用。

### 4.3 图片提示词组装

**问题**：将 B1-B9 卖点、A/B 风格规则、产品上下文组装为 18 条完整的图片生成提示词。

**方案**：
1. 从模板中提取 A 风格和 B 风格的全局约束文本
2. 对每个卖点区块（B1~B9）和每种风格（A、B）进行笛卡尔积组合
3. 将风格约束 + 卖点内容 + 产品上下文 + 画面构图要求拼接为完整提示词
4. 每条提示词包含：比例约束、产品还原约束、韩文文字约束、构图描述、负面提示词

### 4.4 穿戴方向识别（服饰类）

**问题**：宠物服饰类产品的胸腹侧和背部容易在 AI 生图中画反。

**方案**：
1. 在商品画像分析后，若识别为「宠物服饰类」，额外请求模型判断每张参考图的穿戴方向
2. 模型返回 JSON：胸腹侧 / 背部 / 左侧 / 右侧 / 不确定
3. 系统在生图提示词中加入方向约束，确保产品还原准确

## 5. 模板引擎设计

### 5.1 模板体系

系统采用**提示词模板外置**设计，所有生成逻辑通过模板文件驱动：

| 模板类型 | 用途 | 格式 |
|---------|------|------|
| 商品画像模板 | 定义分析维度与输出格式 | Markdown / DOCX |
| 标题模板 | 定义标题风格与 SEO 规则 | DOCX |
| 关键词模板 | 定义关键词分层结构 | DOCX |
| 卖点模板 | 定义卖点组织方式 | DOCX |
| INS 模板 | 定义社媒文案风格 | DOCX |
| 图片提示词模板 | 定义 A/B 风格规则与画面要求 | DOCX |
| 全局约束模板 | 定义图片生成的统一规范 | Markdown |

### 5.2 模板驱动优势

- **运营自主**：调整输出内容时无需修改代码
- **版本管理**：模板支持版本化，可回滚到历史版本
- **多场景复用**：同一套代码支持不同品类、不同市场、不同风格
- **A/B 测试**：可同时维护多组模板，对比生成效果

### 5.3 模板定制指南

运营人员可自定义的内容：
- 角色设定（如「资深韩系电商文案」vs「年轻活泼的社媒达人」）
- 风格要求（如「专业科技风」vs「温情生活风」）
- 输出格式（如增加/减少章节）
- 约束规则（如加强/放松某些禁用词）

**不可修改的内容**（否则可能导致解析失败）：
- 关键占位符结构
- JSON 输出格式要求
- 核心指令逻辑

## 6. 容错与可靠性设计

### 6.1 API 容错

| 错误码 | 策略 | 重试次数 | 间隔 |
|--------|------|---------|------|
| 429（限流） | 固定间隔重试 | 3 | 2s |
| 500/502/503/504（服务端故障） | 固定间隔重试 | 3 | 2s |
| 4xx（客户端错误） | 不重试，直接报错 | 0 | — |

### 6.2 单点失败隔离

- **单张图片失败**：记录错误，继续生成下一张
- **单个产品失败**：记录异常，继续处理下一个产品
- **单张图片读取失败**：跳过该文件，继续处理其他图片
- **模型返回异常格式**：多层 fallback 解析，确保不中断流程

### 6.3 断点续跑

- **全局断点**：支持从指定图片键名恢复（如 A_B4）
- **自动跳过**：`--start-from` 之前的图片即使强制覆盖也不重新生成
- **状态联动**：上游文件变更时，下游依赖自动识别为需重建

## 7. 性能特征

### 7.1 性能基准

| 指标 | 耗时参考 | 瓶颈分析 |
|------|---------|---------|
| 商品画像分析 | 20~40s | 图片上传 + 模型推理 |
| 商品标题 | 10~20s | 模型推理 |
| 关键词 | 10~20s | 模型推理 |
| 详情页卖点 | 30~60s | 输出内容较长 |
| Instagram 文案 | 10~20s | 模型推理 |
| 单张图片生成 | 15~60s | **受模型 API 响应时间制约** |
| **单产品全链路（18 张图）** | **10~30 min** | 图片生成为主要耗时 |

### 7.2 优化方向

- **图片预处理**：参考图缩放到长边 ≤ 1536px，减少传输体积
- **上下文精简**：图片生成前将完整报告精简为摘要上下文，减少 token 消耗
- **缓存复用**：已完成的文件自动跳过，避免重复 API 调用
- **请求间隔**：默认 2 秒间隔，避免触发限流

## 8. 扩展性设计

### 8.1 新增模型线路

1. 新建应用入口
2. 复用现有 IO、解析、编排逻辑
3. 实现新的 Client Adapter 封装目标平台 API
4. 保持输出文件结构和命名完全一致

### 8.2 SaaS 化演进

```
Phase 1: 单机 CLI（当前）
    ↓
Phase 2: 任务队列（Celery + Redis）
    - 异步任务包装
    - Web 层负责上传、触发、查询
    ↓
Phase 3: 引入数据库（PostgreSQL）
    - 产品表、任务表、输出文件表
    ↓
Phase 4: 对象存储（S3/MinIO/OSS）
    - 参考图和生成图持久化
```

## 9. 技术约束与已知限制

| 约束 | 说明 | 应对措施 |
|------|------|---------|
| 无单元测试 | 解析函数的修改需回归验证 | 计划补充 pytest 覆盖 |
| 无类型检查 | 代码为实用脚本风格 | 遵循编码规范 |
| 模型行为依赖 | 不同模型输出格式有差异 | 多层 fallback 解析 |
| 单线程处理 | 当前不支持并发 | 串行处理，未来可引入队列 |
| Windows 环境 | 当前主要在 Windows 运行 | 使用 pathlib 保证跨平台 |
